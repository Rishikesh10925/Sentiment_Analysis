# Deployment guide — Render + Neon

This is the deployment actually prepared for this project: a **static frontend**
and a **Dockerised API** on Render, with **Neon** (managed PostgreSQL) as the
database. No credential is stored in the repository; every secret is set in the
Render dashboard.

```
Browser
  │  https://signal-web.onrender.com        (Render Static Site, React build)
  │
  ├── /api/v2/*  ── CORS ──►  https://signal-api.onrender.com  (Docker, FastAPI)
  │                                   │
  │                                   └── postgresql+psycopg2 (TLS) ──► Neon
  └── static assets from Render CDN
```

## Why this shape

| Choice | Reason |
| --- | --- |
| Neon serverless Postgres | Free tier is enough for a read-heavy demo; no server to patch. |
| Render static site | Frontend is a static bundle; CDN hosting is cheaper and faster than a container. |
| Render Docker web service | The API image is built from this repo (`docker/backend.Dockerfile`), so what is deployed is what CI builds. |
| CPU TF-IDF + logistic regression in production | 3–4 ms/1k rows inference, no GPU, no 270 MB checkpoint. The stronger transformer is reported on the Research page, not served. |

## 1. Database (Neon)

1. Create a Neon project (Postgres 16) in the region nearest your Render region.
2. Copy the **pooled** connection string. It looks like:
   `postgresql://user:password@ep-xxx-pooler.eu-central-1.aws.neon.tech/neondb?sslmode=require`
3. Keep it out of git. `backend/db/session.py` accepts `DATABASE_URL`, rewrites
   `postgres://`/`postgresql://` to the psycopg2 dialect, and demands TLS for
   non-local hosts.

### Load the corpus once

The 1.65M-row parquet files are **not** in git (see `.gitignore`). Build them
locally first, then load straight into Neon:

```bash
# 1. download + curate the public corpora (writes data/curated/*.parquet)
python -m ingestion.real_data

# 2. score the corpus with the serving model
python -m scripts.predict_curated

# 3. create the schema and load everything into Neon
set DATABASE_URL=postgresql://...neon.tech/neondb?sslmode=require
python -m backend.db.migrate
python -m backend.db.load_real_data
```

`load_real_data` is idempotent: it clears and reloads the dashboard tables and
rebuilds the pre-aggregated daily/topic/hashtag/keyword rows. Expect the load
to take a few minutes over a WAN link.

## 2. Render

The repository contains `render.yaml`, so the whole stack can be created with
**New → Blueprint** pointed at the repo. Two services are declared:

| Service | Type | Notes |
| --- | --- | --- |
| `signal-api` | Docker web service | `docker/backend.Dockerfile`, health check `/api/ready`, plan `starter` |
| `signal-web` | Static site | `cd frontend && npm ci && npm run build`, SPA rewrite to `/index.html` |

After the first deploy, set the values the blueprint could not know:

| Variable | Where | Value |
| --- | --- | --- |
| `DATABASE_URL` | `signal-api` | Neon pooled connection string |
| `CORS_ORIGINS` | `signal-api` | `https://signal-web.onrender.com` (comma-separated for more) |
| `API_KEY` | `signal-api` | auto-generated by the blueprint; copy it for uploads |

`VITE_API_BASE_URL` is wired from the API service's `RENDER_EXTERNAL_URL`, so the
static site calls the API directly. Redeploy the static site after the API URL
is known.

### Manual deploy (no blueprint)

API service: Environment → **Docker**, Dockerfile path `docker/backend.Dockerfile`,
context `.`, health check `/api/ready`.

Static site: build command `cd frontend && npm ci && npm run build`, publish
directory `frontend/dist`, rewrite `/*` → `/index.html`, env
`VITE_API_BASE_URL=https://<api-host>`.

## 3. Environment variables

All are read by `backend/settings.py` (pydantic-settings, `.env` supported) or
`backend/db/session.py`.

| Variable | Default | Purpose |
| --- | --- | --- |
| `DATABASE_URL` | — | Managed Postgres URL; overrides the `DB_*` variables |
| `DB_HOST` / `DB_PORT` / `DB_NAME` / `DB_USER` / `DB_PASSWORD` | localhost / 5432 / social_sentiment / postgres / postgres | Local or compose connection |
| `ENVIRONMENT` | `development` | Shown in `/api/v2/meta` |
| `CORS_ORIGINS` | localhost dev origins | Comma-separated allowlist; **must** include the static site origin |
| `API_KEY` | empty (open) | Required `X-API-Key` for `POST /api/upload`; empty disables the check |
| `MAX_UPLOAD_MB` | `50` | Upload size cap, enforced while streaming |
| `RATE_LIMIT_PER_MINUTE` | `120` | Per-IP request budget in the API process |
| `CACHE_TTL_SECONDS` | `120` | Aggregate cache TTL |
| `RESEARCH_CACHE_TTL_SECONDS` | `600` | Research artifact cache TTL |
| `NEGATIVE_SENTIMENT_ALERT_THRESHOLD` | `40` | Alert threshold for dashboard alerts |
| `ENABLE_DOCS` | `true` | Set `false` in production to hide Swagger/OpenAPI |
| `PORT` | `8000` | Injected by Render; the container honours it |

## 4. Verify a deployment

```bash
curl https://<api-host>/api/ready
# {"status":"ready","database":true,"model_artifact":true,"full_reanalysis":false}

curl "https://<api-host>/api/v2/summary?compare=true"
curl "https://<api-host>/api/v2/posts?limit=1"
```

`full_reanalysis: false` is expected in production: the slim API image omits
PySpark, so `POST /api/upload?analyze=true` returns 503 and asks for
`analyze=false`. Validation-only uploads still work.

Then open the static site and confirm the Overview charts populate, the
Research page shows the measured metrics, and the Explorer's explanation drawer
opens (it calls `POST /api/v2/explain`).

## 5. Local production-like stack

```bash
docker compose up --build
# web  -> http://localhost:8080  (nginx, proxies /api to the api container)
# api  -> http://localhost:8000
# db   -> localhost:5434
```

The compose database starts empty; populate it from the host with
`DB_HOST=127.0.0.1 DB_PORT=5434 python -m backend.db.load_real_data`.

## Operating notes and limits

- **Caching is in-process.** `backend/v2.py` memoises aggregates for
  `CACHE_TTL_SECONDS`. With more than one API instance each instance has its own
  cache; move to Redis before scaling horizontally.
- **Rate limiting is in-process** and per IP, keyed on `X-Forwarded-For` when
  present. It is a demo guard, not a defence against a distributed client.
- **Cold starts.** Render free/starter instances sleep. The first request after
  sleep can take 20–60 s; `/api/ready` is the health probe, so Render does not
  route traffic during startup.
- **Cost.** Neon free tier + Render starter API + free static site is roughly
  $7/month for the API instance; the blueprint does not create a paid database.
- **Backups.** Neon keeps point-in-time history on paid plans. For the free
  plan, re-run the loader from the curated parquet — it is the source of truth.
- **Rotating secrets.** Change `API_KEY` in Render and redeploy; the frontend
  prompts for the key at upload time and does not store it.

## Troubleshooting

| Symptom | Cause | Fix |
| --- | --- | --- |
| Overview/trends return 500 with `could not resize shared memory segment` | Postgres container has Docker's 64 MB default `/dev/shm`, too small for parallel aggregates | Set `shm_size: 1gb` on the database service (already in `docker-compose.yml`) and recreate the container |
| `/api/ready` returns 500 | Neon unreachable or `sslmode` missing | Check `DATABASE_URL`; non-local hosts get `sslmode=require` automatically |
| Browser console: CORS error | Static site origin missing from `CORS_ORIGINS` | Add the exact origin (scheme + host, no trailing slash) and redeploy |
| Overview shows zeros | Database not loaded | Run `python -m backend.db.load_real_data` against Neon |
| Uploads return 401 | `API_KEY` set, key missing | Send `X-API-Key`; the UI prompts for it |
| Uploads return 503 | Slim API image, `analyze=true` | Use `analyze=false`, or run the full pipeline in the research environment |
| Research page empty | `results/research/*.json` missing from the image | Rebuild the API image; those files are copied in the Dockerfile |
